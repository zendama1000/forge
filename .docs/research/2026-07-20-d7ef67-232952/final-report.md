## 2. 調査の枠組み

### ロックされた決定事項（調査対象外）

以下5件はユーザー確定事項として、本リサーチでは是非を問わない前提とした。

1. Vite+React での Web アプリ化 / モバイル最適化必須
2. React + three.js を技術の軸に維持（別レンダリング技術への全面乗換えなし）
3. スコープは4領域すべて（新アクション追加 / 既存判定の精緻化 / シナリオ保存・読込 / リプレイ・進行強化）
4. 既存の検証済み判定ロジック（2D版第4弾由来）を土台とし、破棄・全面書き直しはしない
5. 4利用シーン（指導・学習・対戦・素材）すべてを最終対応対象とする

**整合性の結果**: Synthesizer は 5件すべてについて維持を確認、conflicts = 0件。

### 視点構成（固定4 + 動的2 = 6視点、全件成功）

| 視点 | 焦点 | 主要な貢献 |
|------|------|-----------|
| **technical** | 実現性・移植可能性・アーキテクチャ | 実コードを行番号レベルで読解。本件の結論を決定づけた |
| **cost** | 移植工数・投資配分・実行時予算 | rewrite/refactor コスト比、バンドル予算の実測値 |
| **risk** | 退行・誤判定・モバイル性能・スコープ過大 | 決定論が「単一の要」であることの特定、ゴールデンテストの限界 |
| **alternatives** | ロック範囲内の選択肢比較・競合慣習 | 業界慣習（3Dは「見る側」）、保存/共有の実用解 |
| **domain-validity**（動的） | サッカー競技規則との整合・判定の妥当性 | IFAB Law 11 の3層分解、1対1判定の予測不能性の反証 |
| **mobile-3d-interaction**（動的） | モバイル3D操作 UX・現場での成立性 | WCAG 2.5.8 の3D適用、可変速スクラビング、3D直接操作の先例不在 |

**動的視点を立てた理由**: 固定4視点はいずれも「作れるか・いくらか・壊れないか・他案はあるか」という工学的問いであり、**出力される判定がサッカーとして正しいかを誰も検証しない**。本プロダクトの中核価値は判定の妥当性そのものであり、とくにオフサイドは競技規則で公式に定義されているため誤りが即座に信頼喪失につながる。

## 3. 視点別の主要発見

### 3.1 technical — 「コア/描画分離はすでに終わっている」

実ファイル（`C:/Users/bossbot1000tdump/Desktop/football-core/theory-board-3d.jsx`）を読解した唯一の視点であり、本リサーチの結論を決定づけた。

- **判定コア約220行は完全にモジュールスコープの純関数**。定数群（`FREE_THRESHOLD` / `V_BALL` / `V_BASE` / `RUN_TIME` / `MARK_TIGHT` / `HESITATE` / `TIERS`）と `rdist` / `clamp` / `vMax` / `maxRun` / `posAt` / `toWorld` / `laneInfo` / `assignMarks` / `defFrame` / `fromFrame` / `analyzeDefense` / `defenseTargets` は React も THREE も一切参照せず、入出力はプレーンな players 配列のみ。**`export` を足すだけで `core/` へ移設できる**（L11-247）
- **3D層との橋渡しも綺麗**。`stRef.current`（L268, L272-275）が「レンダー時に最新 state をミラーする ref」として一方向ブリッジになっており、rAF描画ループ（L460-520）はこれを読むだけ。**これは zustand の transient update（subscribe / getState）の自作版に相当する**
- **非決定要因は3箇所に特定済み**: L715 `Math.random()`（パス成否判定）、L739 / L760 `Date.now()`（アニメキー）
- **再レンダー・アンチパターンが2件**: L657 の毎フレーム `setAnim`（60fpsでコンポーネント全体が再レンダー）、L820-830 の毎 pointermove `setPlayers`
- **オフサイドは離散ターン制ゆえに構造的に有利**。実サッカーの SAOT で最難関とされる「ボールが蹴られた瞬間の特定」が定義上 `t=0` に確定。`executePass` L733 の `snap` がすでにフリーズフレームで、`laneInfo` はすでに `t` 引数を取り `t=0` で呼ばれている（規約確立済み）
- **ただし重要な非整合が1点**: `analyzeDefense` の `lineNow` は DF の**平均** y（L111）で、規則上の「後ろから2人目（GK 含む）」とは別物。`offsideLine` セレクタを新設し `analyzeDefense` には触れないのが正しい分離
- **モバイル操作の実装はすでに最善手**。ヒットテスト優先 + Pointer Events + `setPointerCapture` + `touchAction:none` により、three.js エコシステムで頻発する DragControls/OrbitControls 競合（issue #20217 / #16254 / #26735）を**そもそも踏んでいない**。残る穴は4点 —（a）`pointercancel` / `lostpointercapture` 未処理、（b）ピンチズーム非対応、（c）ドラッグ slop 不在、（d）ドラッグ中の毎 pointermove `setPlayers`

### 3.2 cost — 「rewrite は構造的に予算を壊す。バンドル予算はすでに赤字」

| 論点 | 数値 |
|------|------|
| refactor vs rewrite | refactor は rewrite の約 **1/3** コスト。rewrite の **67%** が初期予算を50%以上超過、refactor は **85%** が予算内。漸進アプローチは **15か月**早く ROI が黒字化 |
| テスト投資配分 | unit **70%** / 統合 **20%** / E2E **10%**。損益分岐は unit **2-4週** vs E2E **3-6か月**。unit は欠陥の 60-70% をコストの 10-20% で捕捉 |
| バンドル実測（2026-07） | `three` 0.185.1 = **182KB gz** / `@react-three/fiber` 9.6.1 = **51KB gz** / `@react-three/drei` 10.7.7 = **496KB gz** |
| バンドル予算の定説 | クリティカルパス **130-170KB gz**、初回ロード 200KB 未満、総JS 300KB 未満 |
| drei の地雷 | OrbitControls **単体 import** で gzip **273KB** に膨れた実績（drei #2292） |

**帰結**: three.js 単体で予算を超えるため、**3Dバンドルの初期ルートからの分離・遅延ロードは「選択肢」ではなく「前提条件」**。

**投資配分の推奨**: 「横に薄く4シーン」ではなく「縦に1シーンを完成」。共通基盤として置くべきは UI ではなく**決定論的・シリアライズ可能な純粋状態エンジン**で、これが (a) GL 無しの CI 実行、(b) 保存/リプレイのほぼ無償化、(c) テストピラミッドの土台 を一気に成立させる。

**注意**: cost 視点の第5問（「判定＝ルールエンジンが最も高コスト、最終段階に置くべき」）は自身で **confidence: low**、かつ「一次ソースが商用ベンダー（Nected/DecisionRules）に偏り、『自前は高い＝製品を買え』のポジショントークが混入している可能性が高い」と自認している。

### 3.3 risk — 「4つのリスクは独立ではなく、決定論という1点に結合している」

**最重要の構造的発見**: 決定論の設計判断が、①リプレイの端末間再現性、②将来のオンライン対戦の後付け可能性、③ゴールデンテストの厳密一致可能性 — の3つを**同時に**決めてしまう。ここを未決のまま移植を進めると、後から全部が同時に破綻する。

その他の主要指摘:

- **ゴールデンテストは「前と同じか」しか保証せず「正しいか」を保証しない**。2D版に元々あった誤判定を正解として凍結する危険があり、指導用途では最悪の失敗モード。補完手段としてメタモルフィックテスト（平行移動・鏡像反転で判定不変、攻撃方向反転で対称に反転）が有効
- **deliberate play / deflection の判別は「意図」の推定であり、座標入力からは原理的に判定不能**。プロの SAOT ですら重なり・倒れ込み・1〜2フレームのズレで手動フォールバックする
- **モバイル性能の失敗は「時間依存型」**。起動直後は速いが実使用時間で劣化する。合格ラインは**平均 fps ではなくフレーム時間の p95**（ジャンク率）で、屋外相当・15〜20分連続の**実機ソークが代替不能**。「不安定な40〜55fpsより安定した30fpsの方が滑らかに知覚される」
- **iOS Safari の WebGL 制約**: キャンバスリサイズでメモリリークしタブが強制終了する既知の WebKit バグ（bug 219780）
- **保存スキーマのバージョニングは初期コスト極小・失敗コスト甚大**（指導者の資産喪失＝信頼喪失）。バージョンフィールドの後付けは「無版ファイルを版0として推定検出」が必要になり複雑さが跳ね上がる、着手時点で入れるべき典型例
- **リプレイ方式の選択でリスクが桁違いに変わる**: スナップショット方式は決定論を一切要求せず端末差の影響を受けない。22人＋ボール規模なら1フレーム数百バイトに収まる

### 3.4 alternatives — 「業界慣習は『3Dは見る側、2Dは作る側』」

| 論点 | 発見 |
|------|------|
| R3F | 公式が既存 three.js アプリへの段階採用を明示サポート（`useThree` / `<primitive>` / `frameloop="never"`）。`@react-three/test-renderer` は WebGL 不要のヘッドレス検証を与える — **ただし公式に experimental** |
| R3F の警告 | メンテナ自身が「R3F のモデル外で scene の子を直接 add/remove する運用は**いずれ破綻する**」と明言。部分併用は two-world 化リスク |
| 状態管理 | 巻き戻し実装しやすさは valtio ≳ zustand+zundo > jotai > useReducer+Context。ただし **zundo は既定で「値が変化していなくても」履歴を積む**（equality 関数指定は必須） |
| リプレイ | event sourcing 一次情報は「**replay が実測で100msを超えるまで snapshot を入れるな**」と抑制。戦術ボードの1プレーは明確に「短いストリーム」側 |
| 保存・共有 | localStorage 最大10MiB・同期API・文字列のみ / IndexedDB はディスクの50-80%だが **best-effort で eviction されうる**（`navigator.storage.persist()` 要求が必要）/ URL 共有は保守的に **2,000文字**が壁 |
| 業界の配布慣習 | 「**短命な閲覧リンク（配布）＋ ファイルエクスポート（保管）**」に収束。Coach Board、Tactico（72時間失効リンク）、TacticalPad（Drive/OneDrive/Dropbox 同期） |
| スキーマ検証 | Valibot v1.0 = **1.37kB gz** / Zod Mini = **3.94kB** / フル Zod v4 はその10倍規模 |

**最も注意すべき発見**: **3D専業の Tactic3D ですら、作成 UI は2Dで、3Dは「見る」側に限定している**。同社が挙げる3Dの固有価値は「各選手・コーチ・審判の視点＝無制限の視点切替」であって3D直接操作ではない。

**ただし反証あり**: この立て付けは Tactic3D 自身のマーケティング記述からの推論であり、コーチの実利用データや第三者評価ではない（alternatives 自身が caveat に明記）。

### 3.5 domain-validity — 「判定は3層に分離できる。第3層は本質的に確率的」

| 層 | 内容 | 機械化 |
|----|------|--------|
| **第1層** | オフサイドポジションの幾何、判定の瞬間、除外規定（ゴールキック/スローイン/コーナーからの直接受球）。2025/26 追加: GK がボールを投げた場合は最後の接触点基準 | ✅ 可能かつ必須 |
| **第2層** | 「関与」の3類型（interfering with play / with an opponent / gaining an advantage）、deliberate play と deflection の区別（2022-07-27 発効の5基準） | ❌ 意図の推定、機械化に不適 |
| **第3層** | ドリブル成否・1対1の勝敗・守備の良し悪し | ❌ 規則が答えを持たない、本質的に確率的 |

**第3層への強い反証**: UCL 2022/23 の 1,736 ドリブル（成功690 / 失敗1,046）に対し、位置のみ baseline は F1=0.35 / Brier=0.2356。2D特徴で F1=0.49。さらに**3Dポーズ特徴（正規化ボール-足間距離・タッチ頻度・平均アンバランス・胴体傾斜角90パーセンタイル・守備者スタンス角）を足しても F1=0.52 / Brier=0.2429 に留まり、Brier では baseline を下回った**。→ 決定論的な勝敗関数は「それらしいが根拠のない精度」を演出する。**検証可能なのは個別事象の正しさではなく基準率（当該標本で成功率約40%）の再現**。

**margin スカラーへの指摘**: 既存の margin は少なくとも**5つの直交軸**を潰している — (a) goal-side 射影、(b) 密着度、(c) レーン垂直距離、(d) カバー深さ、(e) 相対速度の収束/発散。新アクション追加時の破壊はここから起きる。

**簡略化の正当性には競技自身に前例がある**: US Soccer の PDI（U-9未満はオフサイド不適用、ビルドアウトライン、ヘディング禁止）。ただしこれらは**「明示・公表された改変」であり黙示の近似ではない**点が決定的に重要。

**説明可能性の先例**: TacticAI（DeepMind × Liverpool FC, Nature Communications 2024）は守備側の位置・速度を調整してシュート確率が下がる**反実仮想的な配置を生成**する。成立の必要条件は「**判定関数が verdict と同時に理由構造（どの項が拘束的か・閾値・反転条件）を返すこと**」であり、融合スカラー出力では原理的に忠実な説明を作れない。

**人間側のバイアスに関する警告**: ファウル判定の審判間一致は Cohen's κ = **0.213** と弱い。副審のオフサイド判定は「旗を上げる方向」にバイアスがあり、**このバイアスはコンピュータアニメーション刺激でも観測される** — シミュレータという媒体自体がバイアスを持ち込みうる。

### 3.6 mobile-3d-interaction — 「4問は確立パターンで裏付け、2問は本ドメイン固有の検証ゼロ」

**証拠が強い項目**:

- **ジェスチャ**: 「2本指=パン / ピンチ=ズーム」は model-viewer / p5.orbitControl / OrbitControls すべてで業界共通。争点は「1本指を何に割り当てるか」に集約。ヒットテスト分岐（オブジェクト上=掴む / 空白=回転）が three.js コミュニティおよび Nomad Sculpt（iPad 3Dスカルプト）の実績パターン
- **リプレイ操作**: **可変速スクラビング**（指をタイムラインから縦に離すほど速度が下がる）が iOS / Android / YouTube 共通の確立解。Apple が複数特許を保有。実装例は `ScrubbingSlider`（UISlider サブクラス）、`ScrubbingSpeed.js`
- **タップ領域**: WCAG 2.5.8（AA）は 24×24 CSS px を要求し、判定は「**CSSピクセル基準の画面上サイズ**」で行われる。3Dはカメラ距離で投影サイズが変動するため最悪ケースで割り込む。対策は3層 — ①スクリーンスペースでのヒット球半径の距離補正（target expansion）、②Spacing 例外（中心に直径24px円を置いて交差しなければ可）、③Equivalent 例外（リスト型UIからも到達可能に）

**証拠が弱い項目**:

- 3D視点の自由度: Munzner の **no unjustified 3D 原則**（オクルージョン・遠近歪み・深度の曖昧さ・ナビゲーション複雑化・傾いたテキストの可読性低下）は自由回転に否定的。**ただし同視点自ら反証を記録** — 「Munzner の原則は抽象データ可視化が主対象であり、物理空間の再現（サッカーのピッチ）は『本質的に3次元』側に該当するため、そのまま適用するのは越権の可能性がある」
- シーン別の操作密度・小画面レイアウト優先順位: 一般的モバイル UX 知見（サムゾーン、ボトムシート、屋外の高コントラスト）しか裏付けがなく、**本ドメイン固有の検証事例はゼロ**

**最重要の発見と、その限界**: **3D空間内で駒をドラッグする戦術ボードの先行事例が確認できなかった**。ただし「存在しない」のか「検索で到達できなかった」のかは判別できていない（自認済み gap）。

**視点内で検出された未解決の設計矛盾**: 推奨解である「縦オフセットスクラブ」と「縦方向スワイプ＝カメラ回転」が衝突しうる。この衝突を扱った先行研究・実装例は見つかっていない。

## 4. 統合結論 — 採用する設計解

## 5. 視点間の対立と、その調停

Synthesizer が保存・解決した対立は7件。すべて「握りつぶし」ではなく、対立を明示保存したうえで根拠を示して解決している。

| # | 対立 | 調停結果 |
|---|------|---------|
| 1 | **R3F の扱い**<br>technical「移行の積極的根拠なし」 vs alternatives「test-renderer が決定的利点」 vs cost「rewrite は2〜3倍」 | **素の three.js 維持**。alternatives の最強論拠（test-renderer）は「判定コアがすでに純関数で vitest 直テスト可能」により大半が無力化 — 検証したいのはシーングラフではなく判定ロジックであり WebGL は不要。加えて alternatives 自身が引く R3F メンテナの警告により部分併用は two-world 化リスク。R3F は「新規の宣言的 UI 面が増え、既存シーンを触らずに済む境界が引ける」場合に限る**再評価事項へ降格** |
| 2 | **リプレイのデータモデル**<br>technical「イベントソーシングが正典」 vs alternatives「キーフレーム列が本来のモデル」 | **両立する。層が違う**。イベントログ（seed + コマンド列）を保存・決定論・回帰テストの正典とし、キーフレーム列は再生時にイベントログから導出される**表示上の派生物**。両視点の抑制論（「100ms超えるまで snapshot を入れるな」「全再生1ms未満」）は同じ結論を指す |
| 3 | **決定論化とゴールデンの順序**<br>risk「数値実装を差し替えるとゴールデン等価性と正面衝突」 vs technical「両方を最優先で並列に」 | **「クロス端末での決定論リプレイ」を v1 の明示的な非目標**とすることで解消。同一 JS エンジン内では IEEE754 基本演算で実用上十分 → 数値実装の差し替えは発生しない。唯一の決定論化変更は `Math.random` → シード可能PRNG で、これは**ゴールデン取得より前**に済ませる（順序を固定） |
| 4 | **オフサイド実装の難易度**<br>technical「離散ターン制ゆえ構造的に有利」 vs domain/risk「関与の判定は原理的に不能」 | **評価対象が違う（幾何 vs 法解釈）**。3層化で両立 — Tier A は IFAB 図解を正解コーパスにハードアサーション化、Tier B は自動判定の対象外と明言し手動フラグ、Tier C は断定せず根拠を可視化。簡略化は US Soccer PDI に倣い**「明示・公表された改変」**としてアプリ内に記載（黙示の近似にしない）。準拠した規則の版（シーズン）をテストセットに記録 |
| 5 | **3D直接操作の是非**<br>mobile-3d/alternatives「先行事例なし・no unjustified 3D」 vs technical「技術的障害なし」 | **ロック決定を変えずに慣習側へ寄せられる**。既定の作成用カメラを**俯瞰プリセット（実質2D等価）**とし、自由回転を副・視点プリセットを主とする。これはカメラ初期値と UI 既定値を変えるだけで、既存のヒットテスト・ドラッグ実装はそのまま活きる。3D直接ドラッグは廃止せず俯瞰視点上の操作として残す |
| 6 | **検証投資の配分**<br>cost「E2E は10%に抑えよ」 vs risk「実機15〜20分ソークは代替不能」 | **本数と重みを分離すれば両立**。E2E/L3 は**本数を絞る**（cost 採用）が、残す少数は**実機での walking skeleton** とし、合格判定を平均fpsではなく**フレーム時間 p95** で行う（risk 採用）。視覚的な画素比較は行わず、レンダラ側は数値アサート＋スクリーンショットのスモーク1〜2本に限定 |
| 7 | **既存 margin 判定の扱い**<br>domain「5つの直交軸を潰している」 vs technical「そのまま切り出してゴールデン固定」 vs ロック決定「破棄禁止」 | **additive 拡張で解決**。既存4関数は一切改変せずゴールデン固定し、5軸は**新しい名前付きセレクタとして別途追加**。新アクションは「どの軸を読むか」を宣言する形で実装し、既存 margin へ項を融合しない。`assignMarks` の弱点（CDHMM 論文が認める uninvolved 状態の欠如）は既知の限界として記録し v1 では改変しない |

### DA が指摘した「手元データでは検証不能」な未知（unknowns）

- 実機（低〜中位 Android / iPhone）での15〜20分ソーク時のフレーム時間 p95 と iOS Safari の WebGL メモリ挙動。risk の数値はブログ由来の概算で査読済み計測ではなく、**完了判定が達成可能かは実測前には判定不能**
- tree-shaking 後の three.js の実バンドル増分。cost は 182KB gz を「上限値としてしか使えない」と明記

- 日本の指導現場での配布慣習（LINE 共有 / PDF 印刷等）と端末分布。調査は英語圏中心
- 4シーンのうちどれが最も価値が高いか（risk・cost の双方が判断材料を持たないと記録）

## 8. 非目標と撤退ライン

### 8.1 明示的な非目標（abort として文書化）

| 項目 | 理由 | 機会費用 |
|------|------|---------|
| **クロス端末での決定論的リプレイ再現** | 浮動小数の実装差・JIT最適化差を封じるには固定小数点化や数値実装の差し替えが必要で、ロック決定（既存ロジックを破棄しない）およびゴールデン等価性と正面衝突 | 保存したリプレイを他者端末で共有・再生する機能が v1 では成立しない。**ただし競合のリンク共有は全てサーバホスティング前提であり、純クライアント制約下では元々成立しない経路** |
| **リアルタイムオンライン対戦** | バックエンド不在の現アーキテクチャでは新規プロジェクト相当の再見積りが必要 | 「対戦」の訴求力が同一端末交互操作に留まる。**ただし決定論と一方向データフローを段階0で守れば通信層を後から1箇所に差し込む継ぎ目は残る**（恒久的放棄ではない） |
| **オフサイドの完全自動確定判定（関与・deliberate play を含む）** | 意図の推定は座標入力から原理的に判定不能。実装すれば構造的に誤り続ける | SAOT 的な「審判教育レベルの権威ある判定ツール」のポジショニングは取れず、差別化軸が「判定の断定」→「判定根拠の説明可能性」へ移る。**TacticAI の反実仮想生成と既存 laneInfo の分解済み出力は元々この方向に構造的に適合しており、失うものより得るものが大きい可能性が高い** |

### 8.2 フォールバック案とその発動条件

**フォールバック**: 3D を「見る」専用に降格し、作成・編集は俯瞰オルソグラフィックカメラ固定の擬似2Dレイヤに切り替える（three.js は維持したままカメラと入力層のみ変更）。それでも届かない場合は最終対応対象を4シーン→2シーン（指導・解説 ＋ コンテンツ素材）へ絞り、自主学習・対戦を Phase 4 以降へ繰延。さらにオフサイド Tier A すら際どい帯で信頼を得られない場合は、判定を「断定する機能」から「根拠を可視化して人間が判断する支援機能」へ再定義し、自動 verdict の表示自体を撤去する。

**発動トリガー（いずれか1つで切替）**:

1. 段階0完了後の実機ソークで、低〜中位 Android または iPhone の15〜20分連続稼働時にフレーム時間 p95 が目標を割る、あるいは iOS Safari でタブ強制終了が再現する
2. 22人密集局面での3D駒ドラッグの誤選択率が実機テストで許容外と判明する
3. 指導・解説シーンの walking skeleton が、当初見込みの2倍の作業量を要してもなお通らない
4. Tier A オフサイドのリグレッションスイートで、規則上正しい実装が指導現場の慣習的解釈と繰り返し乖離し、際どい帯の表示だけでは信頼を回復できないと判断される
5. 段階1のバンドルが動的 import 後もクリティカルパス予算（130-170KB gz）を超え、モバイル初回ロードが実用域に入らない

## 9. 採用案に残るリスク（Synthesizer 自認）

1. **ゴールデンテストは「前と同じか」しか保証せず「正しいか」を保証しない**。2D版に元々あった誤判定を正解として凍結する危険。Tier A の IFAB 由来ケース集による正しさ検証を、等価性テストとは**別チャネルとして必ず並走**させること
2. Tier B を手動フラグ化しても、ユーザーが「アプリが判定しないなら関係ない」と解釈して規則誤解を持ち帰る可能性は残る。UI 文言の設計が成否を分けるが、**その効果を測る手段がない**
3. 3D空間での駒ドラッグは先行事例がなく、22人が密集する局面（セットプレー等）でヒットテスト誤選択が許容外になる可能性。俯瞰プリセット既定でも解消しない場合がある
4. 実機ソークでの熱スロットリング・iOS Safari の WebGL メモリ制約が目標 p95 を割る可能性。**これは段階0完了後まで判明しない**
5. 指導・解説を第1スライスに選ぶ判断は、**4シーンのどれが最も価値が高いかの実証データなしに行っている**
6. 「1シーン完成→横展開」は 1シーン目のコードが指導シーン専用に癒着し、2シーン目で大規模改修になるリスク。判定コアが既に分離済みである点が緩衝材にはなるが、**UI 層には同じリスクが残る**
7. zustand 導入は selector による再レンダー最適化を手動適用する必要があり、移行過程で新たな性能退行を持ち込む可能性
8. cost が「最も高コスト」とした判定（ルールエンジン）の評価は、**商用ベンダー由来のポジショントークを含む可能性**があり、本ドメイン固有の複雑度は未検証

## 10. Phase 1.5 へ進む前に決めるべきこと

未解消の DA 指摘のうち、**タスク分解の内容を実際に変える**ものを優先度順に挙げる。

| 優先 | 項目 | 決めるべきこと | 該当 |
|------|------|--------------|------|
| **1** | **保存先ストレージの確定** | どの API を正とするか。alternatives の実用解（IndexedDB=作業データ実体 + `navigator.storage.persist()` 要求 / localStorage=設定と最終開いたIDのみ / JSON エクスポート=正式な配布・バックアップ / URL 共有=圧縮後2,000字以内の補助経路）を採るか。eviction 時のリカバリ方針 | DA-001 |
| **2** | **Tier A の境界定義** | 「点モデルで表現可能な幾何ケースに限る」と明記し、部位差で決まるケースを Tier A から除外するか（＋除外した旨をアプリ内の公表された簡略化として記載）。あるいは身体を点でなく半径/矩形で表現する拡張を含めるか | DA-003 |
| **3** | **確率較正テストの追加** | 多数試行の成功率が事前宣言レンジに収まることを検査するチャネルを検証設計に足すか（domain が示す「基準率約40%の再現」） | DA-007 |
| **4** | **保存ファイルの import 検証** | スキーマ検証ライブラリの採否（Valibot 1.37kB gz / Zod Mini 3.94kB gz / 手書き）と、検証失敗時のフォールバック（バックアップ提示・破棄の可否） | DA-006 |
| **5** | **エクスポートファイルの再生同一性** | キーフレーム（状態列）の任意併記を形式に含めるか、あるいは walking skeleton の「他者に見せる」を同一端末に限定すると明記するか | DA-002 |

加えて、**リサーチでは埋められなかったが実装初期に検証すべき事項**:

- **2D版（第4弾）ソースの所在確認** — ゴールデン凍結の対象が本当に「実地検証済みロジック」かは、これが見つからない限り保証できない
- **IFAB 競技規則第11条の一次資料取得** — technical は SAOT 解説記事を代理出典としており、例外条項・ハーフウェイライン免除の厳密な扱いは未調査
- **tree-shaking 後の three.js 実バンドル増分の実測** — 182KB gz は上限値でしかない
